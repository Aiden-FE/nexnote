选型结论^sec-conclusion

使用 sqlite-vec 作为派生索引，配合 [[FTS5 分词器对比]] 的关键词召回。两者通过统一 Link Index 关联，召回结果再喂给 LLM。详见 [[Link Index 重建策略]]。^p-overview

关键决策

  • embedding 走远程端点（OpenAI 协议），本地小模型留接口
  • 向量与 FTS5 同库不同表，doc_id 关联；不引入 LanceDB
  • 召回三阶段：粗筛 → 双链扩展 → 向量重排（置信度作乘性因子）
风险：向量重建全量会拉高首启动耗时；走「启动时空索引 + 闲置时增量」缓解。
CREATE VIRTUAL TABLE docs_vec USING vec0(
  doc_id INTEGER,
  embedding float[1536],
  distance_metric=cosine
);

关于此原型 · Prototype C

方向

AI 原生驾驶舱 — AI 召回与对话不是外挂面板，而是主组织面。右侧约 40% 宽度的驾驶舱承担「上下文注入 → 渐进召回 → 引用答案」全链路；编辑器退居其次。

绑定的技术栈组合（与 11/12 同栈）

  • 桌面壳: Electron（三端渲染一致，块编辑器生态最稳）
  • 前端: React + TypeScript
  • UI: TailwindCSS + shadcn/ui（CSS 变量需与 ProseMirror 桥接）
  • 编辑器: TipTap 3 + @tiptap/markdown + UniqueID + DragHandle + Suggestion
  • 存储: MD + YAML frontmatter，沿用 Obsidian 公开方言 (^id / callout / wikilink+alias)
  • 索引: SQLite 单库（FTS5 + Link Index + sqlite-vec）
  • Git: simple-git + 默认捆绑 Git(dugite-native)，系统凭证/SSH 环境集成

取舍一句话

三案同栈，差异只在产品形态 / UI 取向。C 的代价 = 编辑器让出近半宽度给右侧 AI 驾驶舱，换取「AI 作为原生层」的可信验证；该方案仅在 AI 确为一级价值时成立（A/B 案若胜出会收回宽度）。

原型内可交互项
