# DEV-108 行末带格式（加粗等）文本的块 ID 锚点序列化后无法回收，切回文档泄漏为可见文本 `^xxxxxxxxx`

## 背景

用户报告：在块文档中加粗了某行文本，切换到另一份文档再切回来，该行行末出现了 `^jhc4x62g5` 这样的异常字符（`^` + 9 位字母数字）。

这是块 ID 锚点（Obsidian 兼容语法 `^id`，内核 UniqueID 扩展为缺 ID 的块自动生成）**泄漏成了可见文本**。

## 现状（triage 核实，含真实代码复现）

块 ID 的双向变换是"占位符法"：parse 前把行末 ` ^id`（或整行 `^id`）替换成 PUA 占位符，parse 后提升为节点 `blockId` 属性；serialize 前把属性注回内联末尾占位符，serialize 后还原为 `^id`。

**两侧不对称导致泄漏**：

- **serialize 侧是 mark 盲的**：占位符被追加进段落的**最后一个文本节点**，直接沿用其 `marks`。行末文本带加粗（斜体/删除线/行内代码/链接同理）时，占位符落在 `**…**` 内部，`finalizeAnchors` 逐行还原后落盘为：

  ```markdown
  段落 **加粗尾 ^jhc4x62g5**
  ```

- **parse 侧只认行末形态**：锚点识别的两个正则都锚定行末（行尾空白 + `^id` + 行尾空白），对上面这行（行末是 `**`）**均不命中**（已用真实正则验证：match = null）。于是 `^jhc4x62g5` 按 marked 的解析进入加粗文本节点，成为**可见文本**；该块的 `blockId` 属性同时丢失，UniqueID 下次会再分配一个新 ID。

**为什么"切换文档"必现**：split 视图只渲染 active tab，切换文档即卸载编辑器（dirty 时先 flush 落盘），key 隔离使切回时全新挂载并从磁盘重新 parse——正好构成完整落盘往返。自动保存（默认 1.5s 防抖）也会把坏行落盘，即使不切文档，重开文档同样复现。

**逐次增长**：泄漏的 `^旧id` 留在行末加粗内，下一次保存 UniqueID 又给该块注入新锚点，落盘变成 `**加粗尾 ^旧id ^新id**`——每切换/保存一次追加一个。

**已做真实内核代码复现**：构造"段落 + 末位文本带 bold mark + blockId"的 JSON 走 `injectPlaceholderForBlockIds` → 占位符落点 marks 为 `[{type:'bold'}]`；落盘行 `段落 **加粗尾 ^vq4x6x1**` 过 `replaceAnchorsWithPlaceholders` 后原样返回（无占位符替换）——泄漏确认。

**对照**：非行末加粗（`普通 **粗体** 普通`）无此问题，因为占位符追加到的末位文本节点无 mark。手写的 `^xxx` 字面量在不带 mark 时按既有防御被保留（不误删）——本票不得破坏该语义。

**测试空白**：round-trip 矩阵有"粗体"与"段落 block ID"用例但没有两者组合；DEV-044 泄漏防御测试的往返循环正文不含任何 mark；DEV-071 修过表格单元格的同类污染但只覆盖 table cell 宿主。**"mark 尾随"形态零覆盖。**

## 期望行为

1. 段落/标题/列表项的末尾文本带任意 inline mark（bold/italic/strike/code/link…）时，块 ID 锚点落盘后**仍能被 parse 侧回收**：切换文档或重开文档后，行末不出现可见 `^id`，块的 `blockId` 保持稳定（不换新 ID）。
2. codeBlock/table 的独立行 `^id` 形态不回归。
3. 用户手写 `^xxx` 字样（非应用生成的锚点、无对应块）在不带 mark 场景的保留语义不回归；带 mark 场景的手写字面量处理行为需在测试中明确锁定。
4. 往返稳定性：parse → serialize → parse → serialize 幂等，不逐次追加新锚点、不逐字符增长。
5. 已被旧版本污染的文档（正文里已有 `^旧id ^新id` 字面量）：**不做自动迁移**（见 Out of scope），但修复后的往返不得继续追加。

## 关键接口

- serialize 侧的内联占位符注入（kernel markdown 管线中"把 `blockId` 属性注回内联末尾"的函数）：需感知末位文本节点的 marks——末位节点带 mark 时，占位符应作为**独立的无 mark 文本节点**插入（落盘后 `**加粗尾** ^id`，恰好是 parse 侧认识的形态），或等价方案。
- parse 侧的行末锚点正则：若选择容忍行尾成对 emphasis/code 闭合定界符（`(\*|~|`)+$`）的方案，须评估与手写 `^xxx` 字面量保留语义的冲突，两种方案不要同时上（会使还原/回收判定复杂化，取其一）。
- 涉及的节点类型集合（paragraph/heading/listItem + codeBlock/table）与锚点语法常量保持不变。
